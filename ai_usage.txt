### 1. В чому головна суть Практики 8?

Ключова ідея цієї практики — **Desugaring (розцукрювання / переписування AST на етапі семантичного аналізу)**.
Ми додаємо дві фічі високого рівня:
1. **Callable Objects (Об'єкти-функтори, Task 1 — 1 бал)**: будь-яку змінну або поле структури, тип якої має метод `call`, можна викликати як функцію: `triple(14)` $\rightarrow$ `triple.call(14)`, а `s.scale(7)` $\rightarrow$ `s.scale.call(7)`.
2. **Lambdas & Closures (Лямбда-функції із захопленням змінних, Task 2 — 1.5 бала + Additional Task `mut` captures — +1 бал)**: функції, які оголошуються прямо всередині коду як звичайний `statement` і захоплюють копії потрібних змінних у квадратних дужках `[k]` або `[mut n]`.

**Чому це «синтаксичний цукор»?**
Тому що в Практиці 7 ми **вже** реалізували структури, поля (`const` та `mut`), методи структур (`MemberFnNode` з неявним першим параметром `this`), виклики методів (`MemberCallNode`) та правило поширення мутацій (`is_mutating`).
- **Callable object** — це просто перетворення виклику `obj(args)` на виклик методу `obj.call(args)`.
- **Лямбда** `fn add_k := [k](i32 y) -> i32 { ... }` — це просто автоматично згенерована компілятором структура `lambda.add_k` з полем `k`, методом `call(i32 y) -> i32` та оголошенням локальної змінної `lambda.add_k add_k{k}` у місці, де стояла лямбда. Як тільки компілятор перетворив лямбду на структуру і змінну `add_k`, виклик `add_k(5)` автоматично стає викликом callable-об'єкта з Task 1!

#### Рівень 2: Парсер ([`Parser`](file:///home/ubuntu/cs400/cs400-course-repo-vkatsel/compiler.py#L429-L1395)) і первинне дерево `--ast`
На етапі парсингу парсер **не знає типів і не знає, чи ім'я є змінною, чи функцією**:
1. **Виклики (`triple(14)` та `s.scale(7)`)**:
   - `triple(14)` парситься у [`parse_factor`](file:///home/ubuntu/cs400/cs400-course-repo-vkatsel/compiler.py#L488-L613) абсолютно так само, як і виклик звичайної функції — у [`CallNode`](file:///home/ubuntu/cs400/cs400-course-repo-vkatsel/compiler.py#L104-L119).
   - `s.scale(7)` вже зараз парситься у [`MemberCallNode`](file:///home/ubuntu/cs400/cs400-course-repo-vkatsel/compiler.py#L122-L139) (`target=VarNode("s")`, `func_name="scale"`).
   - Тому вивід `--ast` для викликів залишається незмінним.
2. **Лямбди (`fn name := [captures](params) -> ret_type`)**:
   - Парсер розрізняє звичайну функцію та лямбду за токеном після `:=`:
     - `fn name := (` — звичайна функція або метод структури (дозволені тільки у секції `fn_defs` на початку програми або всередині `struct`). Якщо така конструкція трапляється серед `statement` або всередині блоку — це помилка парсингу.
     - `fn name := [` — це `LambdaNode` (дозволена всюди, де дозволений `statement`: на top-level серед statements, у тілі функцій, методів, `if`, `while` та всередині іншої лямбди). Якщо `[` стоїть у методі структури — це помилка.
   - У списку захоплень `[...]` парсер зчитує елементи вигляду `ident` або `mut ident` у список `CaptureDef`.

2. **Перевірка і переписування лямбд (Task 2 + Additional Task)**:
   Коли `SemanticChecker` обходить `LambdaNode` (наприклад, `fn add_k := [k](i32 y) -> i32`):
   - **Крок 1 (Перевірка захоплень у зовнішній області видимості)**:
     - Кожне захоплення `c` має бути видимою змінною у точці оголошення лямбди (інакше `cannot capture 'k': no variable 'k' is visible here`).
     - Перевіряємо відсутність дублікатів у `[...]` (`'k' is captured twice`) та те, що жоден параметр не має такого ж імені, як захоплення.
   - **Крок 2 (Створення структури `lambda.<name>` та методу `call`)**:
     - Створюємо синтетичну структуру `lambda.add_k` (оскільки в ідентифікаторах мови не може бути крапки, користувач ніколи не зможе послатися на цей тип напряму або створити колізію).
     - Для кожного захоплення `c` додаємо поле у `lambda.add_k` з типом захопленої змінної та прапорцем `mutable = c.mutable` (`const` для `[k]`, `mut` для `[mut k]`).
     - Додаємо в структуру метод `call` з параметрами, типом повернення та тілом лямбди.
   - **Крок 3 (Перевірка тіла `call` в ізольованій області видимості)**:
     - Тіло лямбди перевіряється точно як метод структури `lambda.add_k`: воно бачить лише свої параметри, свої локальні змінні, поля своєї структури `lambda.add_k` (тобто захоплення!) та глобальні функції.
     - Якщо в тілі використовується змінна із зовнішньої області видимості, якої немає у списку `[...]`, видаємо помилку: `'k' is not captured by lambda 'add_k': add it to the capture list, [k]`.
     - Якщо в тілі робиться присвоєння `k := ...` у `const`-захоплення, видаємо: `cannot assign to 'k': the capture 'k' is const, write [mut k]`.
     - Якщо в тілі змінюється `mut`-захоплення або викликається мутуючий `call` на `mut`-захопленні (наприклад, `[mut next]`), то метод `call` цієї лямбди автоматично стає `is_mutating = True`!
   - **Крок 4 (Створення оголошення змінної-замикання `DeclNode`)**:
     - Після перевірки тіла (тому лямбда не бачить саму себе і не може викликати себе рекурсивно) створюємо `DeclNode` для змінної `add_k` типу `lambda.add_k`, ініціалізованої списком `[VarNode(c.name) for c in captures]`.
     - Якщо хоча б одне захоплення має `mut`, сама змінна `add_k` оголошується як `mut`, щоб виклик `next()` на місці оголошення був дозволений правилом мутацій.
   - **Крок 5 (Заборона використання лямбди як звичайного значення)**:
     - Оскільки тип `lambda.<name>` не має імені в мові, будь-яка спроба передати лямбду як аргумент функції (`sq(times)`), повернути з `exit`, присвоїти, використати в ініціалізації іншої змінної, надрукувати у `print(add_k)` або звернутися до її поля через крапку ззовні (`add_k.k`) блокується у `SemanticChecker` з відповідним повідомленням про помилку.

### 1. Щодо L167: «А якщо під лямбдою теж є глобальні функції, таке ж може бути?»

За граматикою нашої мови (ще з Практики 5–7) програма має суворий порядок секцій:
```ebnf
program ::= { struct_def } { fn_def } { statement } exit ;
```
Тобто:
1. Спочатку йдуть **тільки структури** (`struct_def`).
2. Потім — **тільки глобальні функції** (`fn_def`, без `[...]`).
3. Потім — **інструкції (`statement`)** (змінні, `if`, `while`, `print`, а тепер ще й **`lambda`**) і в кінці `exit`.

Оскільки **лямбда за правилами є саме інструкцією (`statement`)** (бо зазвичай перед нею вже оголошені змінні, які вона захоплює, наприклад `i32 mut k{10}`), то поява першої ж лямбди означає, що ми вже перебуваємо в секції `{ statement }`.

- Якщо під лямбдою йде **інша лямбда** (`fn other := [...]`) — це ще один `statement`, і це **дозволено**.
- А якщо під лямбдою (або під будь-яким іншим `statement`, типу `i32 k{10}`) хтось напише **глобальну функцію** без квадратних дужок (`fn global_fn := (...)`) — це порушення структури програми, і парсер у [`parse_statement`](file:///home/ubuntu/cs400/cs400-course-repo-vkatsel/compiler.py#L1337-L1338) видасть помилку `function declaration after statement` (на це навіть є старий тест у `tests/err/`).

### 2. Щодо L199: «Чи треба обробляти випадки, якщо `.call` змінює немутабельну змінну? Чи ми тільки з копіями працюємо? І те саме щодо лямбд»

**Так, обов'язково треба обробляти!** Тут працюють **два рівні захисту мутабельності**, і обидва ми перевіряємо:

#### Ситуація А: Зміна всередині самого `.call` (або тіла лямбди)
1. **Звичайні зовнішні змінні**:
   До зовнішніх змінних напряму ні метод `.call`, ні лямбда доступу не мають. Лямбда завжди бере **копію** змінної у своє поле під час оголошення (`[k]` або `[mut n]`), тому оригінальна зовнішня змінна ніколи не змінюється.
2. **Поля самої структури або захоплення лямбди**:
   - Якщо у звичайній структурі поле оголошене без `mut` (`i32 k`), або у лямбді змінна захоплена без `mut` (`[k]`), то це поле є **`const`**.
   - Якщо всередині `.call` або тіла лямбди спробувати написати `k := k + 1`, компілятор видасть помилку:
     - для звичайної структури: `cannot assign to const field 'k' inside member function`
     - для лямбди: `cannot assign to 'k': the capture 'k' is const, write [mut k]`

#### Ситуація Б: Метод `.call` змінює `mut`-поле, але сам об'єкт (або захоплена лямбда) є `const`!
Уявімо, що всередині структури чи лямбди поле **дозволено** змінювати (`i32 mut n` у `Counter`, або `[mut n]` у лямбді `next`). Тоді сам метод `call` стає **мутуючим (`is_mutating = True`)** — бо кожен виклик змінює стан самого об'єкта.

А тепер подивімось, як викликають цей об'єкт:
1. **Для об'єкта структури (Task 1)**:
   ```txt
   Counter c{0}      // <-- змінна 'c' створена БЕЗ 'mut' (вона const!)
   i32 a{c()}        // <-- ПОМИЛКА!
   ```
   Хоча поле `n` всередині `Counter` має `mut`, сам об'єкт `c` є `const`. Виклик `c()` намагається змінити `c.n`, тому ми **блокуємо** такий виклик з помилкою:
   `cannot call 'c': its 'call' changes it, and it is not mut`
   (Так само, якщо викликати `s.c()`, де або `s` не є `mut`, або поле `c` всередині `s` не є `mut`).

2. **Для лямбд (Additional Task)**:
   - Коли оголошується `fn next := [mut n]() -> i32`, компілятор знає, що в неї є `mut`-захоплення, і автоматично робить саму змінну `next` мутабельною (`lambda.next mut next{n}`). Тому просто викликати `next()` одразу після оголошення — можна.
   - **АЛЕ** якщо інша лямбда `twice` захоплює `next` **без `mut`**:
     ```txt
     fn twice := [next]() -> i32   // <-- захопили копію 'next' як const!
     {
         i32 a{next()}             // <-- ПОМИЛКА!
         exit a
     }
     ```
     Оскільки `twice` захопила `next` без `mut`, її власна копія об'єкта `next` є **`const`-полем** структури `lambda.twice`. А метод `call` у `next` є мутуючим (`is_mutating = True`)! Тому виклик `next()` всередині `twice` намагається змінити `const`-поле, і компілятор видасть помилку:
     `cannot call 'next': its 'call' changes it, and it is not mut` (щоб запрацювало, треба написати `[mut next]`).
