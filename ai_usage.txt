1. **Лексер (`lexer.py`)**:

2. **Семантика (Двопрохідний аналіз)**:
   - **Pass 1**: Реєстрація всіх типів структур (обчислення індексів полів) та збір сигнатур усіх функцій.

### Відповіді на ключові питання:

#### 1. Чи має LLVM необхідні інструменти?
**Так, LLVM має першокласну підтримку структур:**
* **Іменовані типи (`ir.IdentifiedStructType`)**:
  У `llvmlite` ми створюємо тип структури один раз у контексті модуля:
  ```python
  struct_type = module.context.get_identified_type("Point")
  struct_type.set_body(ir.IntType(32), ir.IntType(32))
  ```
  Це транслюється в LLVM IR як `%"Point" = type { i32, i32 }`.
* **Виділення пам'яті (`alloca`)**: об'єкт структури — це звичайний `alloca` типу `struct_type`.
* **Доступ до полів (`gep` / `GetElementPtr`)**:
  Щоб отримати адресу конкретного поля за його індексом:
  ```python
  field_ptr = builder.gep(slot, [ir.Constant(i32, 0), ir.Constant(i32, field_idx)])
  builder.store(val, field_ptr)
  ```
* **Копіювання всієї структури (`load` + `store`)**:
  У LLVM структура є значенням (*first-class aggregate*). При копіюванні `Point q{p}` або `q := p` можна просто виконати `val = builder.load(src_slot)` і `builder.store(val, dst_slot)`.

#### 2. Як це парсити?
* **Лексер**: додаємо ключове слово `"struct"` та кому `,` (для переліку полів у фігурних дужках `{10, 20}`).
* **Оголошення структури (`struct Name { ... }`)**:
  Читаємо `struct`, ім'я структури, перевіряємо відкриваючу `{` на окремому рядку, зчитуємо поля (`type [mut] ident`) до `}`.
* **Оголошення змінної/об'єкта**:
  У `parse_decl` тепер тип може бути не лише примітивним, а й іменем структури (`ident`). Всередині `{ ... }` зчитуємо список виразів через кому.

#### 3. Як перевіряти семантику?
* **Таблиця структур (`struct_table`)**: реєструє кожну структуру, її поля та їхні числові індекси (0, 1, 2...). Перевіряє, що тип кожного поля вже існує (оголошений вище), що структура не порожня і не посилається сама на себе.
* **Ініціалізація об'єктів**:
  * Якщо передано один вираз того самого типу структури $\rightarrow$ це валідне **копіювання об'єкта** (`Point q{p}`).
  * Якщо передано список виразів $\rightarrow$ їхня кількість та типи повинні точно відповідати полям структури.
* **Заміна цілого об'єкта (`a := b`)**:
  Дозволена лише якщо змінна `a` є `mut`, **ТА** всі її поля на всіх рівнях вкладеності рекурсивно мають модифікатор `mut` (`is_deeply_mutable`).

### 1. Щодо `{` та де саме потрібна уважність

У мові є два принципово різні випадки використання `{}`:

1. **У декларації структури (`struct`) — блоковий синтаксис (як в `if` / `while`)**:
   - Граматика вимагає: `"struct" ident NL "{" NL ... "}" NL`.
   - `{` **мусить бути на окремому рядку**! Якщо хтось напише `struct Point {` на одному рядку $\rightarrow$ помилка (як і `if x == 10 {` у попередній практиці).
   - На рядку з `{` не може бути нічого іншого.
   - Структура не може бути порожньою: якщо наступний рядок одразу `}` $\rightarrow$ помилка `empty struct`.
   - Якщо файл завершився без закриваючої `}` $\rightarrow$ помилка `'{' is never closed`.

2. **В ініціалізації об'єкта (`decl`) — інлайновий синтаксис**:
   - `Point p{10, 20}` або `i32 x{5}`.
   - Тут `{` навпаки відкривається **на тому самому рядку**, де й ім'я змінної.
   - Всередині `{ ... }` міститься список виразів через кому `,`.
   - Порожні `{}` заборонені (має бути щонайменше 1 вираз).
   - Закриваюча `}` має бути на тому ж рядку.

3. **У лексері (`lexer.py`)**:
   - Дужки `{` і `}` лексер уже видає як `Token("block", "{" / "}")`.
   - А от коми `,` (ASCII 44) в лексері зараз взагалі немає (викидає `unexpected byte ','`), тому її обов'язково треба додати.

### 2. Щодо трьох нод в AST — спрощуємо до однієї

Ти абсолютно правий — створювати три окремі ноди AST для структури це явний over-engineering.

Нам потрібна **лише одна нова нода AST**:
* **`StructDefNode(line, col, name: str, fields: list[FieldDef])`** — представляє оголошення структури на верхньому рівні програми.
  *(де `FieldDef` — це не вузол дерева, а просто легкий датаклас опису поля: `name`, `type_name`, `mutable`, `line`, `col`)*.

А решта вже покривається наявними конструкціями:
* **`DeclNode`**: просто розширюємо поле з `init: ExprNode` на `inits: list[ExprNode]`:
  * Для примітиву `i32 x{5}` $\rightarrow$ `inits = [ConstNode(5)]` (1 елемент).
  * Для структури `Point p{10, 20}` $\rightarrow$ `inits = [ConstNode(10), ConstNode(20)]` (2 елементи).
  * Для копіювання `Point q{p}` $\rightarrow$ `inits = [VarNode("p")]` (1 елемент того самого типу).
* **`AssignNode`**: уже існує (`AssignNode(name, value)`) і повністю підходить для заміни цілого об'єкта `q := p`!

### Наступний крок: **Task 2 — Функції (`fn`)**

Згідно з [w06-practice.md](file:///home/ubuntu/cs400/.agents/w6-files/w06-practice.md), функції мають таку специфікацію:

1. **Синтаксис оголошення**:
   ```text
   fn check := (i32 x, bool flag) -> bool
   {
       i32 mut y{3}
       if flag
       {
           y := y + x
       }
       bool result{y == 10}
       exit result
   }
   ```
2. **Параметри та скоуп**:
   * Параметри передаються за значенням (копії) і є константними всередині тіла (`const`).
   * Повна **ізоляція скоупу**: тіло функції бачить виключно власні параметри, свої локальні змінні та всі функції програми. Топ-левел змінні всередині функції **недоступні**.
3. **Оператор `exit`**:
   * Усередині функції `exit` діє як `return` (повертає значення відповідного типу; дозволені ранні `exit` усередині `if`; останнім стейтментом блоку функції обов'язково має бути `exit`).
   * На топ-левелі `exit` завершує роботу програми.
4. **Взаємні та рекурсивні виклики**:
   * Функція може викликати саму себе або функцію, оголошену нижче за неї.
   * Для цього в семантиці реалізується **двопрохідний аналіз**: спочатку збираються всі сигнатури, потім перевіряються тіла.
5. **LLVM IR**:
   * Кожна функція створюється як `ir.Function` з префіксом (наприклад, `user_{name}`), щоб уникнути колізій з `main` та `printf`.
   * Параметри копіюються в слоти `alloca` у вхідному блоці `entry`.
   * `exit` у функції транслюється в `builder.ret(val)`.
   * Виклик функції транслюється в `builder.call(fn, args)`.
   * Дозволено неявне розширення аргументу `i32` у параметр `i64`.

### Як реалізувати функції (Task 2)

Для реалізації функцій потрібні такі кроки у кожному з компонентів компілятора:

#### 1. Лексер (`lexer.py`)
* **Ключове слово `"fn"`**: додаємо в `KEYWORDS`.
* **Оператор `"->"`**: при обробці символу `-` (ASCII 45), якщо наступний символ `>`, токенізуємо як `Token("operator", "->")`, інакше — звичайний мінус.
* **Дужки `(` та `)` (ASCII 40, 41)**:
  * Додаємо в лексер (як `Token("punctuation", "(" / ")")`).
  * *Нюанс*: мова не підтримує групування дужками в арифметиці (наприклад, `(2 + 3)`). Тому в `parse_factor()`, якщо несподівано зустрічається `(`, парсер викидає `unexpected byte '('` — це повністю зберігає поведінку попередніх практик і наявних тестів.

#### 2. Вузли AST (`compiler.py`)
* **`ParamDef(name: str, type_name: str, line: int, col: int)`** — датаклас опису одного параметра.
* **`FnDefNode(name: str, params: list[ParamDef], return_type: str, body: BlockNode, line: int, col: int)`** — вузол оголошення функції.
* **`CallNode(func_name: str, args: list[ExprNode], line: int, col: int)`** — вузол виклику функції (фактор виразу, який має тип `return_type` цієї функції).
* У **`ProgramNode`**: додаємо список `fn_defs: list[FnDefNode]`.

#### 3. Парсер (`Parser`)
* **Фіксований порядок**:
  $$\text{program} ::= \{\text{struct}\} \; \{\text{fn}\} \; \{\text{statement}\} \; \text{exit}$$
  Після секції `struct` парсимо всі `fn ...`. Якщо функція зустрінеться після звичайного стейтменту $\rightarrow$ викидаємо помилку `function declaration after statement`.
* **`parse_fn_def()`**:
  * Зчитуємо `fn <name> := (` $\rightarrow$ список параметрів `type ident` через кому $\rightarrow$ `) -> <type>` $\rightarrow$ блок тіла `{ ... exit ... }`.
* **`parse_factor()`**:
  * Коли зустрічаємо `ident`, заглядаємо на наступний токен:
    * Якщо наступний токен `(` $\rightarrow$ це виклик функції `parse_call()`. Зчитуємо вирази-аргументи через кому до `)`.
    * Інакше $\rightarrow$ звичайна змінна `VarNode`.

#### 4. Семантичний аналіз (Два проходи)
Оскільки функції можуть бути взаємно рекурсивними або викликати функції, оголошені нижче:
* **Прохід 1 (Збір сигнатур)**:
  * Проходимо по всіх `fn_defs` і записуємо в словник:
    `self.functions[name] = FnInfo(params, return_type)`.
  * Перевіряємо унікальність імені та валідність типів параметрів і типу повернення.
* **Прохід 2 (Перевірка тіл)**:
  * Для кожної функції створюємо новий **ізольований скоуп** (`self.scopes = [{}]`).
  * Параметри додаються в скоуп як константи (`mutable=False`). Глобальні змінні функції **не бачать**.
  * Запам'ятовуємо `self.current_fn = fn_info`.
  * У `visit_exit`:
    * Якщо `self.current_fn` активна $\rightarrow$ перевіряємо, що тип повернення `exit` збігається з `return_type` функції.
    * Якщо на топ-левелі $\rightarrow$ як і раніше, перевіряємо примітивний тип (`i32`, `i64`, `bool`).
* **Перевірка виклику `visit_call`**:
  * Перевіряємо існування функції, кількість аргументів та типи аргументів (з підтримкою `i32` $\to$ `i64`). Встановлюємо `node.type = fn_info.return_type`.

* **Оголошення функції**:
  ```python

  ```
* **Оператор `exit`**:
  * Усередині користувацької функції: генеруємо `self.builder.ret(exit_val)`.
  * У `main` (топ-левел): генеруємо `printf` + `ret i32 0`, як і раніше.
* **Виклик `CallNode`**:
  ```python

  ```

### Чому для функцій потрібні два кроки?

З функціями діє інше правило з завдання практики:
> *"A function can call any function of the program, also itself or one declared below it."*

Приклад:
```text
fn foo := (i32 x) -> i32
{
    exit bar(x)    # bar оголошена НИЖЧЕ!
}

fn bar := (i32 y) -> i32
{
    exit y + 1
}
```

Якщо перевіряти в один лінійний прохід:
Коли чекер перевіряє тіло `foo`, він бачить виклик `bar(x)`. Але `bar` ще не оголошена! Компілятор видав би помилку `unknown function 'bar'`. Те саме в LLVM: модуль не зміг би згенерувати інструкцію `call`, бо функція `bar` ще не створена в модулі.

```python
    for s in node.struct_defs:

    # Зберігаємо тільки: ім'я, типи параметрів і return_type.
```

   ```text
   Circle mut c{p, 10}
   c.radius := 5        # ОК: і c є mut, і поле radius оголошене як mut

   c.center.x := 25     # ПОМИЛКА: хоч c — mut, і x у Point — mut, але проміжне поле center у Circle оголошене як const!
   ```

3. **Суворий порядок програми**:
   ```text
   program ::= { struct } { fn } { statement } exit
   ```

### Як це реалізувати технічно?

#### 1. AST (Дерево)
- Замість окремих штучних вузлів ми додаємо вузол:
  ```python
  @dataclass(slots=True)
  class FieldAccessNode(ExprNode):
      obj_name: str           # наприклад, 'c'
      fields: list[str]       # наприклад, ['center', 'x']
      # Заповнюється в семантичному проході:
      decl: DeclNode | None = field(default=None, init=False)
      field_indices: list[int] = field(default_factory=list, init=False) # [0, 0] для GEP!
  ```
- Для `AssignNode`:
  Замість просто `AssignNode(name: str, value: ExprNode)` робимо універсально:
  ```python
  @dataclass(slots=True)
  class AssignNode(StmtNode):
      target: str | FieldAccessNode  # або ім'я змінної, або ланцюжок доступу
      value: ExprNode
  ```
  Це елегантно охоплює і `a := 5`, і `c.center.x := 5`.

#### 2. Семантичний аналіз (`SemanticChecker`)
- При перевірці `FieldAccessNode`:
  1. Знаходимо `decl = lookup(obj_name)`.
  2. Стартуємо з типу `cur_type = decl.type_name`.
  3. Для кожного поля `f_name` в `fields`:
     - Перевіряємо, що `cur_type` є структурою, і вона має поле `f_name`.
     - Запам'ятовуємо його числовий індекс `idx` у списку `field_indices`.
     - Якщо це операція **запису** (L-Value): перевіряємо, що початковий об'єкт `decl.mutable == True` **ТА** кожне поле в ланцюжку має `field_info.mutable == True`. Якщо хоч одне не `mut` — кидаємо помилку з точним повідомленням.
     - Оновлюємо `cur_type = field_info.type_name`.
  4. Результуючий тип виразу `node.type = cur_type`.

#### 3. Генерація LLVM IR (`CodeGenVisitor`)
- **GEP (GetElementPtr)**:
  Вся краса в тому, що генератор коду не знає імен полів — він бере вже підготовлені індекси!
  ```python
  # slot — це Alloca адреса об'єкта
  ptr = slot
  # Для кожного індексу в ланцюжку робимо:
  # builder.gep(ptr, [0, idx])
  ```
- Для **читання** — робимо `builder.load(ptr)`.
- Для **запису** — робимо `builder.store(val, ptr)`.
