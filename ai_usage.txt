### 🗺️ Загальна схема конвеєра (Pipeline)

Коли ви запускаєте `python3 compiler.py program.txt output.ll`, програма проходить 4 послідовні фази:

```
[Вихідний текст]
       │
       ▼
1. ЛЕКСЕР (lexer.py)              ──> Перетворює символи на потік слів (Tokens)
       │
       ▼
2. ПАРСЕР (compiler.py: Parser)   ──> Перевіряє граматику і будує дерево (Raw AST)
       │
       ▼
3. СЕМАНТИЧНИЙ ПРОХІД             ──> Перевіряє типи, змінні, mut і декорує дерево
   (compiler.py: SemanticChecker)     (приписує node.type та node.decl)
       │
       ▼
4. ГЕНЕРАТОР КОДУ (CodeGenVisitor)──> Сліпо довіряє дереву і випускає LLVM IR
       │
       ▼
  [output.ll] ──> Виконується через `lli` або компілюється в машинний код
```

  - Зустрів `x` — розуміє, що це ім'я змінної (ідентифікатор).

#### 2. Синтаксичний аналіз / Парсер (`compiler.py: Parser`)
- **Завдання:** Перевірити, чи складені токени у правильні речення згідно з граматикою, та побудувати **абстрактне синтаксичне дерево (AST)**.
- **Як працює:**
  Парсер використовує метод рекурсивного спуску. Він знає структуру мови:
  - Оголошення — це `тип + [mut] + ім'я + { + вираз + }`.
  - Пріоритет операцій: `factor` (число/змінна/true/false) $\to$ `term` (`*`) $\to$ `arith` (`+`, `-`) $\to$ `expr` (`==`, `!=`).
  - Парсер **не знає**, чи існує змінна `x`, і **не знає**, чи сумісні типи. Він лише будує структуру зв'язків.
- **Результат (сире дерево в пам'яті):**
  ```text
  ProgramNode
   ├── DeclNode (name="x", type_name="i32", init=ConstNode(10))
   ├── DeclNode (name="y", type_name="i64", mutable=True, init=VarNode("x"))
   └── ExitNode (value=VarNode("y"))
  ```

---

#### 3. Семантичний прохід (`compiler.py: SemanticChecker`) — **Головна суть Week 4**
- **Завдання:** Перевірити *сенс* програми (чи оголошені змінні, чи правильні типи, чи не присвоюємо в константу) **ДО того, як створюється хоч один рядок IR**.
- **Чому це критично:**
  У Практиці 3 перевірки робилися всередині генератора коду. Якщо десь була помилка, генератор падав на середині побудови інструкцій. Тепер це незалежний прохід.
- **Як працює:**
  Клас `SemanticChecker` обходить дерево методом `visit_*`:
  1. Має власну таблицю символів: `self.symbols = {}` (мапить `назва -> DeclNode`).
  2. Коли бачить `DeclNode("x")`:
     - Перевіряє, чи ім'я `"x"` вже є в `symbols` (захист від повторного оголошення).
     - Обчислює тип виразу ініціалізації: для `ConstNode(10)` це `"i32"`.
     - Перевіряє сумісність через `check_assignable(have="i32", want="i32")` — OK.
     - Записує `symbols["x"] = decl_x`.
  3. Коли бачить `DeclNode("y")`:
     - Обчислює вираз `VarNode("x")`: дивиться в `symbols`, знаходить `"x"`, прив'язує його: `node.decl = decl_x`, тип — `"i32"`.
     - Перевіряє `check_assignable(have="i32", want="i64")` — дозволено, бо це **widening (розширення)**!
  4. Кожному вузлу виразу проставляє атрибут `node.type`, а кожній змінній — `node.decl`.
- **Результат:** 
  Якщо є помилка — одразу викликається `CompileError(line, col, msg)` і програма зупиняється. Якщо помилок немає — на виході маємо **декороване (типізоване) дерево**, якому можна на 100% довіряти.

---

#### 4. Генерація коду (`compiler.py: CodeGenVisitor`)
- **Завдання:** Перекласти декороване дерево в інструкції низькорівневої мови LLVM IR.
- **Контракт із семантичним проходом:**
  `CodeGenVisitor` **не робить жодних перевірок**! Він не шукає змінні у таблиці за назвами — він просто читає `node.decl` та `node.type`.
- **Ключові механізми генератора:**
  1. **Пам'ять:** Для кожного `DeclNode` викликає `builder.alloca(тип)` і зберігає вказівник прямо у вузол `node.alloca`.
  2. **Widening (`sext`):** В LLVM не можна виконати команду над різними типами (наприклад, додати `i32` до `i64`). Тому у всіх місцях, де семантичний аналізатор дозволив приведення `i32 -> i64`, генератор вставляє команду знакового розширення:
     ```llvm
     %wide = sext i32 %x to i64
     ```
  3. **Порівняння (`icmp`):** Генерує цілочисельне порівняння `icmp eq` або `icmp ne`, яке повертає 1-бітне булеве значення (`i1`).
  4. **Вихід (`exit`):** 
     - Якщо число — друкує через `printf("Program exit with result %lld\n", %val)`.
     - Якщо `bool` — за допомогою команди `select` без жодних розгалужень обирає між адресою рядка `"true"` та `"false"` і передає у `printf`.

### 🎯 Що вимагає Task 2 за специфікацією (1.5 бала):

1. **Окремий клас `SemanticChecker`**:
   - Запускається на всьому AST **до того**, як створюється генератор коду `CodeGenVisitor`.
   - Повністю володіє **таблицею символів** (`self.symbols: dict[str, DeclNode]`).
   - Прив'язує кожній змінній вузол її оголошення (`node.decl = decl`), а кожному виразу — обчислений тип (`node.type = "i32" | "i64" | "bool"`).

2. **Винесення старих перевірок з CodeGen**:
   - `variable '...' is used before its declaration` (використання до оголошення).
   - `variable '...' is already declared` (повторне оголошення).
   - `cannot assign to '...': it is not mut` (присвоєння константі).
   - *Важливо:* з `CodeGenVisitor` ці перевірки повністю прибрано — генератор більше взагалі не шукає імена в словнику, а сліпо довіряє полю `node.decl.alloca`.

3. **Правила системи типів (Type Rules)**:
   - **Константи:** найвужчий тип, у який вони вміщуються:
     - $0 \le x \le 2^{31}-1 \implies \mathbf{i32}$
     - $2^{31} \le x \le 2^{63}-1 \implies \mathbf{i64}$
     - $x > 2^{63}-1 \implies$ помилка переповнення `constant <val> does not fit in i64`.
   - **Арифметика (`+`, `-`, `*`):** тільки цілі числа; результат — ширший тип (`i32 + i64 = i64`). Булеві значення заборонені: `cannot apply '+' to bool`.
   - **Порівняння (`==`, `!=`):** два числа (будь-якої ширини) або два bool; результат — `bool`. Змішування bool з числом — помилка: `cannot compare bool with i32`.
   - **Присвоєння та ініціалізація (`check_assignable`):**
     - Дозволено тільки однаковий тип або `i32 -> i64` (**widening**).
     - Будь-яке звуження (**narrowing**, `i64 -> i32`) заборонено:
       - `cannot initialise 'b' of type i32 with a value of type i64`
       - `cannot assign to 'x' of type i32 with a value of type i64`
     - Змішування булевих і числових типів заборонено.
   - **`exit`:** приймає тільки цілі числа або `bool`.

### 2. Стан виконання Task 2 (Semantic Pass — 1.5 бала)

Ось що саме вимагає специфікація Task 2 і що наразі реалізовано:

1. **Окремий клас `SemanticChecker`**:
   - Запускається на дереві AST **до** створення інструкцій IR.
   - Володіє таблицею символів (`self.symbols: dict[str, DeclNode]`).
   - Декорує дерево: записує `node.type` кожному виразу та `node.decl` кожній змінній.
   - Старі перевірки (declared before use, declared once, `mut` before `:=`) **повністю прибрані з `CodeGenVisitor`** — генератор більше не шукає імена в словнику, а напряму читає `node.decl.alloca`.

2. **Правила типізації**:
   - `+ - *` вимагають цілих чисел; булевий операнд викликає помилку: `cannot apply '+' to bool`.
   - `== !=` вимагають або два числа, або два `bool`. Змішування викликає помилку: `cannot compare bool with i32`.
   - Константа автоматично отримує найвужчий тип: $\le 2^{31}-1 \implies \mathbf{i32}$, $\le 2^{63}-1 \implies \mathbf{i64}$, більше $\implies$ помилка переповнення.
   - `check_assignable`: дозволяє лише однаковий тип або `i32 -> i64` (**widening**). Будь-яке звуження (**narrowing**) відхиляється.
