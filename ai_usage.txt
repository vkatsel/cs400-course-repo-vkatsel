## 2. What Was Taken, Changed, and Why

- **What was taken as generated**:
  - The implementation of `UseCounter`, `Pruner`, and the fixpoint loop in `remove_unused`, counting uses per declaration (`id(decl)`) instead of variable names, keeping expressions with `read()` or function calls, and supporting the `--remove-unused` CLI flag anywhere in the arguments.
  - Tracking global function call counts (`fn_calls`) inside `UseCounter` and removing uncalled `FnDefNode` definitions from `ProgramNode.fn_defs` in the same fixpoint loop as unused variables.
  - The `EffectAnalyzer` pass and `has_effect` helper for the additional task (detecting `print`, `read()`, `while`, struct field mutations, and recursion via a fixpoint loop so pure calls are removed).
  - The updated `tests/run_tests.py` script that tests `tests/opt/` (comparing both `--ast-checked` output against `.astc` and program output against `.expected`), the 10 optimization test cases in `tests/opt/`, the `weakref_slot=True` addition on `Node`, and the `## Optimizations` section in `README.md`.
- **What I changed / adapted and why**:
  - Initially, the AI placed the whole optimization pass directly inside `compiler.py`. Since `compiler.py` was already getting too large, I asked to move all optimization logic into a separate `optimizer.py` file and import `remove_unused` from there.
  - I reviewed the logic to make sure only top-level functions in `fn_defs` are removed and that removing a dead function also triggers removal of functions or variables that were only used inside it on the next iteration.
  - Manually tested edge cases from the terminal (shadowed variables in nested blocks, `FieldAssignNode` on dead structs, chained unused functions, and self-referential loops like `k := k + 1`) to verify the pass before committing.

А кожен блок у дереві (`ProgramNode` або `BlockNode`) влаштований дуже просто:
```text
BlockNode
 ├── statements: [ Stmt_1, Stmt_2, Stmt_3, ... ]   <-- звичайний список Python!
 └── exit: ExitNode (окреме поле, яке ніколи не видаляється)
```
Кожен `DeclNode` чи `AssignNode` — це просто окремий елемент у списку `statements`, від якого вниз росте лише його власне піддерево (вираз ініціалізатора `{10}` або права частина присвоєння `:= 20`). Від самого `DeclNode` ніякі інші інструкції блоку «вниз як діти» не ростуть.

### У чому полягає Additional Task (+1 бал) — "Calls without effects"

У **Task 1** ми використовували дуже консервативне правило:
> *Якщо ініціалізатор змінної чи вираз у `:=` містить будь-який виклик функції (`CallNode` / `MemberCallNode`), ми вважаємо це побічним ефектом і завжди зберігаємо змінну та виклик.*

Але насправді більшість викликів (наприклад, чисті математичні функції типу `square(3)`) **нічого не друкують, нічого не читають і не змінюють пам'ять**. Якщо результат такого виклику ніхто не читає (`i32 a{square(3)}`), його можна безпечно видалити!

#### Суть додаткового таску:
Замість `has_call_or_read`, ми видаляємо невикористану змінну навіть тоді, коли її вираз містить виклик функції, **якщо ця функція не має спостережуваних побічних ефектів**.

Змінна чи присвоєння залишаються тільки тоді, коли вираз містить `read()` або виклик функції, яка має **effect**:

1. **Прямі ефекти**:
   - Функція у своєму тілі містить `print` або `read()`.
   - Це мутуюча member-функція структури (вона змінює стан об'єкта, на якому викликана: наприклад, `c.bump()`).
   - Функція може не повернутися (зависнути/зациклитися): її тіло містить `while`, або вона рекурсивно викликає себе напряму чи через цикл. Зациклення є спостережуваним ззовні, тому такі виклики не можна викидати.
2. **Транзитивні ефекти**:
   - Функція викликає іншу функцію, яка має ефект (наприклад, `relay` викликає `loud`, яка робить `print`).
   - Оскільки функції можуть викликати одна одну, множина функцій з ефектами обчислюється як **fixpoint**: починаємо з перших трьох правил і додаємо тих, хто їх викликає, поки множина не перестане змінюватися.
   - Для callable-об'єктів (лямбд чи структур із `call`) — це перевірка їхнього методу `call`.

#### Приклад з методички:
```text
fn square := (i32 a) -> i32 {
    i32 r{a * a}
    exit r
}
fn quiet := (i32 a) -> i32 {
    exit square(a)
}
fn loud := (i32 a) -> i32 {
    print(a)
    exit a
}

i32 a{square(3)}   # Чиста: немає print/read/while/mutation -> видаляється
i32 b{quiet(4)}    # Викликає чисту -> чиста -> видаляється
i32 c{loud(5)}     # Робить print -> МАЄ ЕФЕКТ -> ЗАЛИШАЄТЬСЯ
exit 0
```
- **Без додаткового таску** (Task 1): `a` і `b` залишаються, бо містять виклики.
- **З додатковим таском**:
  1. Ітерація 1: `a` і `b` видаляються.
  2. Ітерація 2: функція `quiet` більше ніким не викликається -> видаляється.
  3. Ітерація 3: функція `square` більше ніким не викликається -> видаляється.
  4. Залишається тільки `loud`, оголошення `c` та `exit 0`. Програма виводить `5` і виходить з `0`.

Також перевіряються:
- `c.bump()` (мутуючий метод) — зберігається.
- `c.peek()` (лише читає поле) — видаляється, якщо результат не використовується.
- функції з `while` або рекурсією — зберігаються.

### Крок 1. Визначення «ефектів» функцій (Effect Analysis)

- Member-функція структури / лямбди: `("struct_name", "method_name")`

Ми проходимо по тілу кожної функції й збираємо:

   - Чи є `WhileNode`?

2. **Які інші функції вона викликає:**

### Крок 2. Обчислення циклів (рекурсії) та замикання (Fixpoint)

1. **Рекурсія / потенційне зациклення:**
   - Будуємо граф викликів між функціями `caller -> callee`.
   - Якщо з функції `f` можна по графу дійти назад до самої `f` (пряма чи взаємна рекурсія), вона позначається як така, що має ефект (бо рекурсія може не завершитися).
2. **Поширення ефектів (Fixpoint):**
   - Робимо простий цикл `while changed`:
   - Якщо функція `A` викликає функцію `B`, і `B` позначена як така, що має ефект, то й `A` стає функцією з ефектом (`effects.add(A)`).
   - Повторюємо, поки множина не перестане рости.

### Крок 3. Перевірка виразів: `has_effect(expr)` замість `has_call_or_read(expr)`

Зараз у нас було:
```python
def has_call_or_read(expr):
    match expr:
        case ReadNode() | CallNode() | MemberCallNode():
            return True
        ...
```

А тепер буде:
```python
def has_effect(expr, effect_fns):
    match expr:
        case ReadNode():
            return True
        case CallNode(func_name=fn):
            # Якщо це глобальна функція з ефектом
            return fn in effect_fns
        case MemberCallNode(struct_name=st, func_name=m):
            # Якщо це метод або call лямбди з ефектом
            return (st, m) in effect_fns
        case BinOpNode(left=l, right=r):
            return has_effect(l, effect_fns) or has_effect(r, effect_fns)
        ...
```

---

### Крок 4. Інтеграція в цикл оптимізації `remove_unused`

На кожній ітерації нашого циклу:
1. Аналізуємо ефекти актуальних функцій у дереві -> отримуємо множину `effect_fns`.
2. Запускаємо `UseCounter(effect_fns)`.
   - Декларації `DeclNode` та присвоєння `AssignNode` залишаються (`self.read(decl)`), тільки якщо `has_effect(value, effect_fns) == True`!
   - Якщо у виразі стоїть чистий виклик (наприклад, `square(3)`), `has_effect` повертає `False`, тому змінна **не** вважається прочитаною і може бути видалена!
3. `Pruner` викидає мертві змінні та функції з `0` викликів.
4. Оскільки видалення `i32 a{square(3)}` прибирає виклик `square(3)`, на наступній ітерації `square` матиме 0 викликів і видалиться сама функція.

Все працює в єдиному ітеративному циклі.
